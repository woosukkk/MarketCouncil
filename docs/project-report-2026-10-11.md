# MarketCouncil 개발 보고서

## 1 프로젝트 개요와 개발 목적

작성자 이우석  |  작성일 2026년 10월 11일  |  구현 및 검증 기록 기준 2026년 10월 10일

MarketCouncil은 기업의 금융 데이터와 문서 근거를 수집하고, 상승 관점과 하락 관점의 AI가 서로의 가설을 검토하도록 만든 투자 리서치 시스템이다. 하나의 답변만 읽는 대신 어떤 사실에서 해석이 갈리는지, 무엇이 아직 확인되지 않았는지, 결론을 바꾸려면 어떤 자료가 필요한지를 보여주는 데 목적이 있다.

현재 시스템은 로컬 PC에서 분석을 실행하고, 웹에서는 저장된 결과와 인용 근거를 열람하는 구조로 구현했다. React와 Vercel이 웹 화면을 제공하며 Supabase가 인증과 사용자별 결과, 공유 상태, 관리자 성능 기록을 관리한다. 큰 원문 파일과 임베딩 데이터는 로컬에 두고, 클라우드에는 분석 결과와 필요한 인용문을 보관한다.

핵심 성과는 근거 기반 토론을 사용자 서비스로 연결한 것이다. 삼성전자 실제 분석 1회에서 2라운드 토론을 생성했고, 결과를 비공개로 저장한 뒤 공식 토론으로 공개하는 흐름을 확인했다. 로그인, 관심기업, 분석 북마크, 개인 결과 가져오기, 공유 및 관리자 페이지도 구현했다. 다만 이 사례가 투자 판단의 정확도나 환각 감소 효과를 입증하지는 않는다.

### 문제 정의

일반적인 생성형 AI 답변은 결론이 자연스럽게 보이더라도 출처가 없거나, 과거 수치와 최근 사건을 혼합하거나, 가능성을 사실처럼 표현할 수 있다. 또한 한 가지 관점에서 답변을 생성하면 반대 근거가 충분히 드러나지 않을 수 있다. 본 프로젝트는 외부 근거 연결, 역할별 가설 검토, 미해결 쟁점 표시를 통해 이러한 문제를 검토 가능하게 만드는 접근을 선택했다.

### 개발 범위

기업 분석, 근거 검색, 다회차 토론, 결과 보관과 공개, 사용자 인증, 검색 성능 평가 도구를 포함한다. 자동매매, 수익 보장, 금융 전문가의 판단 대체는 범위에 포함하지 않는다. 모든 기능이 완전한 상용 운영 수준으로 검증된 것은 아니며, 구현 여부와 실제 검증 범위를 본 보고서에서 구분한다.

### 보고서 구성

2장은 전체 구조, 3장은 AI 토론, 4장은 RAG 검색, 5장은 환각 완화 장치, 6장은 사용자 서비스와 저장 구조, 7장은 성능 평가, 8장은 한계와 향후 과제를 설명한다. 내용의 근거는 프로젝트 소스와 개발 기록이며, 별도 실험으로 확인되지 않은 효과는 기대 효과 또는 검증 과제로 표현한다.


## 2 전체 구조와 데이터 처리 방식

분석 과정은 기업명 입력에서 시작한다. 기업명 조회로 종목 후보를 찾고, 금융 데이터와 공시, 로컬 문서, 최신 웹 자료를 수집한다. 모호한 기업명이 여러 종목에 해당하면 후보 확인이 필요하며, 기업명을 입력하는 것만으로 모든 회사의 자료가 준비되는 것은 아니다.

### 기술 구성

| 구분 | 사용 기술 | 담당 기능 |
| --- | --- | --- |
| 분석 실행 | Python과 LangGraph | 자료 수집과 토론 단계의 상태 및 분기 관리 |
| 언어 모델 | OpenAI API와 gpt 5 mini 설정 | 역할별 분석과 중재자 검토 및 요약 |
| 문서 검색 | BAAI bge m3와 ChromaDB | 문서와 질문 임베딩 및 유사도 검색 |
| 외부 근거 | Open DART와 SEC EDGAR 및 금융 자료 | 공식 공시와 재무 및 가격 자료 수집 |
| 웹 수집 | SearXNG와 Crawl4AI | 관련 페이지 탐색과 본문 추출 |
| 사용자 화면 | React와 Vite 및 Vercel | 소개 페이지와 토론 열람 및 마이페이지 |
| 인증 및 저장 | Supabase Auth와 Postgres 및 Storage | 로그인과 개인 결과 및 공개 결과 보관 |
| PC 배포 | Windows 실행 프로그램 | 사용자 PC에서 분석과 로컬 저장 실행 |

### 처리 흐름

기업명 확인 → 금융 및 문서 근거 수집 → 공통 근거 카탈로그 구성 → 상승 및 하락 최초 분석 → 중재자의 의제 선정 → 역할별 발언과 반론 → 쟁점 상태 검토 → 종료 판단과 최종 정리 → 로컬 저장 → 선택적 웹 업로드와 공개.

LangGraph는 위 단계의 실행 순서와 상태 전달을 관리한다. 그래프를 사용한다고 사실성 검증이 자동으로 해결되는 것은 아니다. 검색 필터, 인용 검증, 프롬프트, 종료 조건 등 각 단계의 구체적인 로직이 결과 품질을 결정한다.

공통 금융 자료와 통합 문서 문맥을 바탕으로 양측 분석을 구성한다. 역할별 검색 결과와 웹 문맥에는 차이가 있을 수 있으므로 모든 입력이 완전히 동일한 실험이라고 볼 수는 없다. 토론 단계에서는 양측 분석과 공통 근거 카탈로그를 함께 제공해 근거를 비교할 수 있게 한다.

재무 원본과 계산 지표를 분리하고, 현금흐름과 수익률, 변동성, 부채 및 희석 관련 지표를 분석 문맥에 포함한다. 시장 국면 비교는 과거 상승과 최근 하락 구간을 함께 검토하도록 돕는다. 자료 수집 실패나 데이터 부족은 한계로 남겨야 하며, 누락을 모델의 추정으로 채우는 것은 지양한다.


## 3 AI 역할별 토론의 작동 원리

### 역할과 질문의 분리

Bull은 제공된 자료에서 상승 가설을 구성하고, Bear는 하락 위험과 반대 근거를 검토한다. Moderator는 충돌하는 의제를 선택하고 각 라운드의 쟁점 상태와 다음 질문을 정리한다. 같은 모델에 서로 다른 역할과 지시를 주는 구성으로, 서로 독립적인 전문가나 서로 다른 모델의 합의 시스템은 아니다.

중재자는 최초 분석과 공통 근거에서 실제로 충돌하는 의제를 최대 3개 선정한다. 같은 사건에서 파생된 주장을 하나의 쟁점으로 합치고, 양측이 답할 수 있는 검증 질문으로 바꾼다. 쟁점은 OPEN, CONTESTED, RESOLVED, STALEMATE, UNKNOWN 상태로 관리한다. UNKNOWN은 필요한 자료가 없어 현재 입력으로 검증할 수 없다는 의미다.

### 라운드와 종료 조건

한 라운드에서는 상승 관점 발언, 하락 관점 반론, 중재자 검토가 순서대로 실행된다. 하락 역할은 현재 상승 발언을 보고 반박할 수 있으므로 실행 순서의 영향을 받을 수 있다. 이후 라운드에는 이전 발언과 중재 질문을 전달한다. 최소 2라운드를 진행하며 최대 3라운드를 넘기지 않는다.

2라운드 이후 계속하려면 중재자의 계속 판단뿐 아니라 OPEN 또는 CONTESTED 쟁점이 남아 있어야 한다. 이전 전체 라운드와 비교해 새로운 유효 인용이 있거나, 중재자가 실질적 변화와 그 이유를 제시해야 한다. 새 정보 없이 같은 주장을 반복하면 종료한다. 최대 라운드 제한은 반복과 호출 증가를 제한하지만 정확도를 보장하는 규칙은 아니다.

최종 정리는 합의점, 미해결 쟁점, 추가로 필요한 증거를 제시한다. 여러 AI가 같은 결론에 도달했다는 사실만으로 그 결론을 참으로 취급하지 않는다. 중재자도 언어 모델이므로 근거를 잘못 해석할 수 있으며, 인용 확인과 사실 판단을 분리해야 한다.

### 새로운 시각을 제공하는 방식

예를 들어 투자 지출 증가는 성장 설비 확보라는 상승 가설과 단기 현금흐름 부담이라는 하락 가설로 해석될 수 있다. 이 사례는 방식 설명을 위한 예시이며 실제 삼성전자 결과를 인용한 것은 아니다. 토론은 두 해석이 갈리는 가정과 기간을 드러내고, 설비 가동률이나 현금흐름 추세 같은 추가 확인 질문으로 연결한다.

따라서 새로운 시각은 없는 사실을 만들어내는 것이 아니라 같은 근거의 대안적 해석과 반증 조건을 보여주는 데서 나온다. 새로운 관점의 유용성은 사용자 또는 전문가 평가로 확인해야 하며, 에이전트 수나 발언량을 그 자체로 품질 지표로 삼지 않는다.


## 4 RAG 검색과 근거 연결

RAG는 질문에 관련된 자료를 먼저 검색한 뒤 그 자료를 언어 모델의 입력에 포함하는 방식이다. 모델의 기억만으로 답변을 구성하는 부담을 줄이고, 사용자가 원문을 추적할 수 있는 근거를 제공한다. 본 프로젝트의 로컬 검색은 문서를 청크로 나누고 BAAI bge m3로 임베딩한 뒤 ChromaDB에서 질문과 가까운 청크를 찾는다.

### 문서 검색 과정

기본 텍스트 분할 함수는 1000자 길이와 200자 중첩을 사용한다. 이는 토큰 단위 설정이 아니며 전체 수집 경로가 모두 동일한 분할 설정을 사용하는지는 별도 확인이 필요하다. 중첩은 경계에서 문맥이 끊기는 문제를 완화하지만, 표나 문단의 의미 단위를 보존하지 못할 수도 있다.

현재 ReportRetriever는 BGE M3의 밀집 임베딩을 사용한다. 질문을 벡터로 바꾸고 요청 개수의 최대 3배를 후보로 검색한 뒤 날짜와 순위 규칙을 적용한다. BGE M3가 지원하는 모든 검색 방식을 사용하는 것은 아니며, 키워드 검색과의 결합이나 별도 신경망 재순위 모델은 현재 검색기의 구성으로 확인되지 않았다.

기업명과 자료 유형으로 후보를 제한하고, 기준일 이후에 발행된 자료는 제외한다. 유사도 거리와 자료의 오래된 정도, 공시 유형에 따른 가산 벌점을 합쳐 순위를 정한다. 현재 이 규칙의 품질 개선 폭은 측정하지 않았다. 후보 검색 뒤 날짜를 제외하므로 유효 결과가 요청 개수보다 적어질 수도 있다. 발행일이 없는 자료는 시간 검증이 제한된다.

### 근거 카탈로그

검색된 문서와 웹 자료, 금융 근거를 카탈로그에 모으고 source ID와 quote ID를 부여한다. 토론은 이 식별자를 사용해 근거를 연결한다. 문서 제목, 주소, 날짜, 페이지와 실제 인용문을 결과에 연결해 사용자가 어떤 자료가 어떤 주장에 쓰였는지 확인하도록 한다.

동일 문서의 동일 청크는 중복을 줄이지만, 다른 출처가 같은 기사를 재전송한 경우까지 모두 독립성 검증이 끝난 것은 아니다. 근거의 개수는 독립적인 증거의 개수와 다를 수 있다. 공시, 언론 보도, 의견, 영상 가설은 성격과 신뢰 수준을 구분해 읽어야 한다.

RAG는 검색하지 못한 사실을 대신 보증하지 않는다. 정답 자료가 없거나 검색에서 누락되면 입력이 불완전해지고, 자료가 있어도 모델이 잘못 해석할 수 있다. 따라서 검색 성능과 답변 사실성을 별도로 평가하는 구조가 필요하다.


## 5 환각을 줄이기 위한 장치와 남은 위험

환각은 근거 없이 만들어낸 사실이나 잘못 연결한 수치와 출처를 자연스럽게 제시하는 문제를 말한다. 본 프로젝트는 여러 장치를 적용했지만, 환각 감소율을 측정한 실험은 아직 수행하지 않았다. 아래 표의 효과는 장치가 차단하거나 드러내는 오류 유형을 설명하며 실제 개선율을 의미하지 않는다.

| 적용 장치 | 다루는 오류 | 남는 한계 |
| --- | --- | --- |
| 기업명 및 기준일 필터 | 다른 기업과 미래 자료 혼입 | 메타데이터가 틀리거나 누락되면 한계 |
| 공통 근거 카탈로그 | 출처 없는 발언과 자료 추적 어려움 | 자료 자체의 오류와 편향은 남음 |
| 인용 쌍 검증 | 존재하지 않는 출처 및 인용 식별자 | 실제 인용이 주장을 지지하는지는 별도 |
| 원문 인용 복원 | 모델이 인용문을 변형하는 문제 | 앞뒤 문맥과 의미 해석은 추가 검토 필요 |
| 사실과 가설 구분 지시 | 가능성을 확정 사실로 표현하는 문제 | 프롬프트 준수와 중재 판단은 불완전 |
| 반대 관점과 미해결 표시 | 한쪽 해석과 과도한 확신 | 같은 모델의 오류가 양측에 반복될 수 있음 |
| 반복 종료 및 라운드 제한 | 새 근거 없는 장시간 토론 | 종료 시점의 정확성과 결론 진실성은 별도 |

### 프로그램으로 확인하는 부분

토론 발언의 source ID와 quote ID가 제공된 카탈로그에 실제로 존재하는지 확인한다. 없는 인용은 유효 근거 목록에서 제외하고 citation errors에 남긴다. 존재하는 인용은 카탈로그의 원문으로 복원해 citation valid를 표시한다. 이 검사는 인용의 존재 확인이며, 인용 내용이 발언의 결론을 논리적으로 뒷받침한다는 판정이 아니다.

JSON 스키마를 사용해 발언 구조를 제한하고, 불완전한 응답에는 제한된 재시도를 수행한다. 형식 검증은 결과를 처리 가능하게 만들지만 잘못된 내용까지 바로잡지는 못한다. 초기 자유형 분석이나 최종 요약의 모든 문장을 같은 강도로 프로그램 검증하는 것도 아니다.

### 모델 지시와 사용자 검토가 필요한 부분

입력에 없는 수치 추가 금지, 확인 불가 표시, 사실과 시장 기대 및 가설 구분은 프롬프트에 반영한다. 영상 주장은 확정된 금융 사실로 취급하지 않고 검증할 의제 후보로 다룬다. 실제 수집 여부와 품질은 외부 서비스와 자료 접근 상태에 따라 달라질 수 있다.

남는 핵심 위험은 잘못된 원문, 선택적 인용, 출처 간 비독립성, 같은 모델의 공통 편향, 오래된 자료, 외부 문서의 악성 지시다. 외부 문서 지시에 대한 전용 방어 성능이나 사실성 자동 판정은 검증되지 않았다. 중요한 판단에서는 원문 대조와 사람의 검토가 필요하다.


## 6 사용자 서비스와 결과 저장 구조

### 사용자 이용 흐름

웹에서는 이메일 또는 GitHub로 로그인하고, 마이페이지에서 관심기업과 저장한 분석을 확인한다. 관심기업 등록은 목록 관리이며 자동 분석 실행이 아니다. 개인 분석을 실행하려면 Windows 프로그램이나 로컬 소스를 사용해 분석한 뒤 결과 JSON을 가져오는 방식으로 이용한다.

개인 토론은 기본적으로 본인만 읽을 수 있다. 사용자가 링크 공유 또는 커뮤니티 공개를 선택한 경우 해당 범위로 열람할 수 있다. 공유 링크를 해제해도 이미 읽거나 복사한 내용은 회수할 수 없다. 공식 토론은 운영자가 날짜별로 지정하며, 현재 삼성전자 분석 후 공식 게시 흐름을 준비했다. 예약 실행이 아니라 버튼 기반 실행이다.

분석 서버와 웹 열람 서버를 분리했으므로, 게시된 결과는 분석을 수행한 PC가 꺼져 있어도 웹에서 열람할 수 있다. 반면 새 분석은 로컬 PC와 필요한 API 및 검색 서비스가 준비돼 있어야 한다. 결과를 저장소에 추가할 때마다 화면 코드를 다시 배포할 필요는 없으며, 화면 기능 변경에는 웹 배포가 필요하다.

### 공간과 비용을 줄이는 저장 방식

PDF 원문, 수집한 기사 본문 전체, 검색 문맥, 임베딩과 Chroma 파일은 로컬에 두고, 클라우드에는 선택된 분석 필드와 실제 인용 근거를 저장한다. 관심기업과 북마크는 자료 사본 대신 참조와 기업 정보를 보관한다. 이 방식은 사용자별 원문 중복 저장을 줄이지만, 인용문과 토론 결과가 누적되면 저장 공간은 계속 증가한다.

실제 공개한 삼성전자 결과는 약 77KB였다. 단일 사례의 크기이므로 모든 결과의 평균 크기로 간주할 수 없다. 단순한 크기 예시로 77KB 결과 1000개는 약 77MB이며, 데이터베이스와 인덱스, 백업 등 추가 사용량은 별도다. 원문 전체를 저장하지 않아도 출처의 제목과 주소, 인용을 보관해 검토 경로를 남긴다.

### 접근 권한과 배포

Supabase의 행 수준 보안은 사용자 ID를 기준으로 개인 목록과 결과 접근을 제한한다. 관리자 기록은 공식 운영자만 읽고 본인 명의로 추가하도록 구성했다. 비밀 키는 프런트엔드와 배포 파일에 포함하지 않으며, 공개 브라우저 키의 사용은 데이터베이스 권한 정책을 전제로 한다.

Windows 0.4.0은 폴더형 배포이며 ZIP 크기는 약 451MB, 압축 해제 후 약 1.19GB다. 다운로드 크기가 작아진 것은 아니며 매 실행 시 전체 런타임을 풀던 절차를 제거했다. 패키징은 소스의 완전한 은닉을 보장하지 않는다. 서버 분석 비용 부담을 줄이는 대신 사용자 설치와 기기 자원이 필요하며 OpenAI 사용료는 별도로 발생한다.


## 7 성능 모니터링과 RAG 벤치마크

관리자 페이지에는 운영 모니터링과 RAG 벤치마크 탭을 구현했다. 실제 측정 JSON을 가져와 관리자 전용 저장소에 보관하고 기록을 비교한다. 추정치나 예시 점수를 실제 결과처럼 표시하지 않으며, 업로드한 표본만 집계한다. 전체 서비스의 실시간 관제 시스템은 아니다.

### 현재 측정과 검증 결과

| 항목 | 확인한 결과 | 해석 범위 |
| --- | --- | --- |
| 삼성전자 실제 분석 | 1회 실행과 2라운드 결과 생성 | 단일 실행 흐름 확인 |
| 결과 보관 및 공개 | 비공개 가져오기와 공식 공개 및 비로그인 열람 | 공개 결과 서비스 흐름 확인 |
| 웹 성능 | Lighthouse 모바일 점수 63점과 LCP 약 4.91초 | 2026년 10월 10일 실험실 측정 1회 |
| 관리자 기록 | 실제 성능 파일 저장 및 새로고침 후 재조회 | 저장소 연결과 관리자 UI 확인 |
| 기록 접근 제한 | 비로그인 읽기 거부와 일반 계정 조회 0건 | 관리자 기록의 접근 정책 확인 |

| RAG 검색 품질 | 평가 도구와 페이지 구현 | 실제 정답 데이터셋 점수는 미측정 |

웹 성능 측정의 TBT는 0ms, CLS는 약 0.147이었다. 이 값은 이전 웹 버전 0.9.2에서 측정한 모바일 실험실 기록이며, 현재 관리자 기능의 모든 화면이나 실제 방문자 평균을 대표하지 않는다. 분석 총시간, 단계별 지연, 토큰과 비용의 실제 기준값은 아직 없다.

### 검색 평가 원리

고정 질문마다 기업명, 기준일과 정답 문서 또는 청크를 지정하고 현재 검색기를 반복 실행한다. Recall은 정답 근거 중 검색된 비율, Precision은 검색 결과 중 정답 비율, MRR은 첫 정답 순위의 역수다. p95는 관측 검색 시간의 상위 구간을 나타내며 기업 혼입, 기업 미상, 기준일 이후 자료 수도 기록한다.

평가에는 LLM 호출이 필요하지 않는다. 모델 준비를 위한 첫 검색은 시간 집계에서 제외하고, 데이터셋과 문서 저장소 해시, 모델명, 검색 개수와 반복 수를 보관한다. 빈 저장소나 평가 중 변경된 저장소는 거부한다. 질문과 원문은 업로드 기록에 포함하지 않는다. 검색 코드와 모델 세부 버전까지 완전히 고정한 재현 실험은 추가 준비가 필요하다.

소스 실행에는 분석 시간과 CPU 시간, 성공 및 실패를 저장하는 수집기를 추가했다. 기존 PC 배포 0.4.0에는 이 수집기가 없다. 토큰과 비용, 답변 사실성 및 인용의 의미 적합도는 현재 평가 범위에 포함되지 않는다.


## 8 한계와 향후 검증 계획

### 현재의 결론

MarketCouncil은 근거 수집부터 역할별 토론, 인용 추적, 개인 보관과 선택적 공개까지 연결한 프로토타입이다. 사용자가 결론뿐 아니라 반대 논거와 불확실성을 확인할 수 있도록 구성했다는 점이 핵심이다. 검색과 인용 검증, 반복 종료는 오류를 발견할 수 있는 절차를 제공하지만, 환각 감소와 판단 개선 효과는 별도 실험으로 입증해야 한다.

### 다음 평가 과제

첫째, 실제 문서에서 사람이 검토한 고정 질문과 정답 근거를 구성한다. 검색 개수, 날짜 조건과 저장소를 동일하게 유지하고 현재 검색 규칙의 Recall과 MRR, 지연을 측정한다. 자료 유형과 발행 시기, 기업을 나눠 결과를 확인하면 어느 조건에서 누락이 발생하는지 알 수 있다.

둘째, 같은 기업과 기준일에서 단일 답변, RAG 단일 답변, RAG 역할별 토론을 비교한다. 각 주장에 원문이 있는지, 원문이 실제로 주장을 지지하는지, 수치와 기준일이 맞는지, 확인 불가를 적절히 표현하는지 사람이 평가한다. 외부 검색 자료와 모델 설정, 실행 순서, 반복 수를 통제하고 비용과 지연도 함께 기록한다. 이는 향후 계획이며 수행한 벤치마크가 아니다.

셋째, 새로운 관점이 유용한지를 평가한다. 단순 문장 다양성보다 중요한 반대 근거를 발견했는지, 검증 가능한 추가 질문을 제시했는지, 가설의 강화 및 폐기 조건이 구체적인지를 확인한다. 모델 평가를 보조로 사용할 수 있지만 동일 모델의 자기평가만으로 성과를 확정하지 않는다.

넷째, 새 PC 설치와 전체 버튼 실행 및 공식 게시를 검증하고 성능 수집기를 다음 패키지에 반영한다. 대규모 동시 사용자, 장기 저장량, 메일 발송 한도와 공유 정책도 운영 전 확인해야 한다. 비용 절감 구조가 서비스의 무제한 무료 운영을 보장하지는 않는다.

### 구현 근거와 확인 경로

소스 저장소는 https://github.com/woosukkk/MarketCouncil 이다. 웹 서비스는 https://frontend-six-pi-h5i7tztups.vercel.app 이며 관리자 페이지는 운영자 로그인 후 app?view=admin에서 열람한다. 최근 웹 배포 태그는 web-v0.10.1이고 관리자 성능 기능의 개발 이슈는 저장소 이슈 15번이다.

주요 구현 근거는 app/debate_workflow.py와 agents/analysis_debate_agent.py 및 agents/moderator_prompt.py, rag/retriever.py와 rag/text_splitter.py, tools/evidence_catalog.py다. 서비스와 검증 기록은 docs/desktop-distribution.md, docs/result-publishing.md, docs/user-service.md, docs/admin-performance.md 및 supabase/discussions.sql에서 확인할 수 있다. 기존 문서 일부는 과거 단계의 기록이므로 최신 코드와 실제 검증 기록을 함께 확인했다.

본 보고서는 코드 및 개발 기록을 정리한 구현 보고서다. 과거 실행을 다시 수행하거나 신규 유료 분석, 실제 정답 기반 RAG 평가를 실행하지 않았다. 구현된 절차, 확인된 사례와 기대 효과를 구분해 제시했다.
